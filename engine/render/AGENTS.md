# Shared Rendering Instructions

Read this file for every material, shader, texture, mesh, render-technique, render-pass, or shared GPU-resource change. If implementation becomes backend-specific, also read the corresponding backend guide.

## Architectural boundary

Actual source is under `gbCore/sources`; runtime render content is under `gbBundle`. The renderer provides shared types such as `graphics_context`, `render_pipeline`, render techniques, `render_pass_descriptor`, `material`, `shader`, `texture`, `vbo`, and `ibo`, but backend branches remain inside several of those classes. Treat it as a partial facade, not a fully interchangeable RHI.

Normal application rendering is data-driven:

1. An entity has transformation, geometry, and material components.
2. A material is indexed by a configured technique name.
3. Transition XML composes ordered world-space (WS), screen-space (SS), and output techniques.
4. `ces_render_system` enumerates renderable entities and submits draws.
5. `render_pipeline` executes SS/output work and asks the platform context to present.

Do not put a one-off visual effect directly into `ces_render_system`.

## Where code and content belong

- Reusable shared renderer behavior: `gbCore/sources`.
- Shader sources: `gbBundle/Shaders` and Metal counterparts under `gbBundle/Shaders/metal`.
- Material XML: the applicable subtree of `gbBundle/Configurations/**/materials`.
- WS/SS technique XML: `gbBundle/Configurations/techniques`.
- Transition pass composition: `gbBundle/Configurations/transitions`.
- Application selection/orchestration: the owning `gbDemo` transition or scene.
- New serialized fields: schema input under `gbCore/configurations`, then regenerate `gbCore/autogenerated`; never hand-edit generated code.

## Canonical patterns to copy

- Configured mesh/material creation: `gbCore/sources/scene_fabricator.cpp::create_shape_3d()` and `add_materials()`.
- Draw traversal/submission: `gbCore/sources/ces_render_system.cpp`.
- Pipeline execution: `gbCore/sources/render_pipeline.cpp`.
- Material setup: `gbBundle/Configurations/game_objects/materials/material.arrow.base.xml` and `gbCore/sources/material.cpp`.
- Texture loading: `gbCore/sources/material.cpp::set_textures()`.
- Shader pair: `gbBundle/Shaders/shader_arrow.vert` and `.frag`.
- Render-pass composition: `gbBundle/Configurations/transitions/transition.main_menu.xml`, `gbBundle/Configurations/techniques/ws_techniques/ws.technique.base.xml`, and `gbCore/sources/game_transition.cpp`.

Use `CODE_PATTERNS.md` for the minimal snippets and why these examples are canonical.

## Adding a mesh or material use

- Prefer `scene_fabricator` and configuration over assembling GPU state in gameplay code.
- A procedural mesh still needs the appropriate geometry component and a material associated with a technique used by the active transition.
- `material::construct()` copies configured state; shader and texture setup are separate loading calls.
- Add a material to the entity through `ces_material_component`/`ces_material_extension` using the configured technique name.
- PNG is the only evidenced working general texture-loading path. The `.pvr` branch is incomplete; do not rely on it.

## Adding or changing a shader

- External GLSL uses paired `<base>.vert` and `<base>.frag` files and material XML references `<base>` without an extension.
- OpenGL compiles/links the GLSL pair.
- Vulkan converts the GLSL pair through shaderc to SPIR-V modules.
- Metal does not translate this GLSL at runtime. Add matching `vertex_<shader-guid>` and `fragment_<shader-guid>` functions to a `.metal` source included in the applicable Xcode target/default library.
- Follow existing attributes, uniform names, sampler indices, buffer bindings, and backend conventions. Do not create a second naming scheme for one shader.

## Adding a render pass

For a prompt such as “Add a render pass for outlines”:

1. Identify the target transition and whether the effect needs a WS geometry pass or an SS fullscreen pass. If the prompt leaves multiple materially different target transitions/effect models, ask one focused question rather than changing all transitions.
2. Copy the closest technique XML under `gbBundle/Configurations/techniques`.
3. Give it a unique GUID and intentional order after inspecting all existing techniques in that transition.
4. Configure attachments, dimensions, clear state, and material using fields already supported by generated configuration types.
5. Reference the technique XML from the target transition XML.
6. Add or update the material and cross-backend shader implementations using the same technique/GUID naming convention as neighboring passes.
7. Use attachment textures through the custom-resource names registered by `game_transition::on_activated()` when a later pass consumes them.
8. Add C++ only if existing WS geometry or SS fullscreen technique behavior cannot express the pass. Do not create a new technique subclass merely to register another configured pass.

An outline algorithm is not implied by the phrase “outline pass.” Geometry expansion, stencil outlines, edge detection, and ID-buffer outlines have different data/attachment needs; establish the intended existing analogue before implementation.

## Cross-backend rules

- Backend selection is in `gbCore/sources/gl_commands.hpp`: current source branches select Vulkan on Windows and Metal on macOS/iOS/tvOS; OpenGL code paths exist but are not currently selected.
- A change to `material`, `shader`, `texture`, `vbo`, `ibo`, `render_pass_descriptor`, render techniques, or `ces_render_system` requires inspection of every backend branch in that file.
- OpenGL manages framebuffer state in techniques. Vulkan and Metal use common `render_pass_descriptor` wrappers backed by native implementations.
- Keep backend-native calls behind existing backend classes/guards. Application and ECS code should remain at mesh/material/technique level.
- Do not move GPU resource creation/commit to the resource serializer thread.

## What not to touch

For a normal shader, material, or configured pass, do not modify:

- `gbCore/sources/ces_render_system.cpp`
- `gbCore/sources/render_pipeline.cpp`
- `gbCore/sources/gl_commands.hpp`
- `graphics_context_*` presentation code
- Vulkan/Metal synchronization or singleton teardown
- `gbCore/autogenerated/*`

Do not edit `gbWin32SharedResources` as the canonical copy of an asset. Change `gbBundle` and let staging copy it.

## Build and test

No automated renderer test suite was discovered. Minimum verification for a shared render change:

1. Validate referenced XML/shader/texture filenames and confirm unique technique order/GUID within the target transition.
2. Build the Windows Vulkan demo when available:

   ```powershell
   ./gbScripts/build-gbDemo.ps1 -Configuration debug-client -Platform x64
   ```

3. Run the demo through the affected transition and inspect a frame containing the affected material/pass.
4. Check validation/compiler/runtime output for shader, pipeline, attachment, and synchronization errors.
5. Build and run relevant Apple targets for shared changes that affect Metal.
6. Follow the OpenGL guide if the dormant GL path is in scope.
7. State which backends were not built or visually exercised. Do not claim parity from one backend.
