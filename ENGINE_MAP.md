## Verification scope and evidence rules

This map was verified by reading declarations, implementations, project metadata, scripts, and representative application call sites. File presence proves an implementation path exists; it does **not** prove that every platform target currently compiles or runs. Negative statements mean a repository-wide filename/text search found no matching engine-owned implementation; external tooling and omitted files remain `UNKNOWN`.

## Entry points and application lifecycle

**Purpose.** Create the native application/window, construct engine services, activate a configured transition, and drive frame updates.

**Important classes.** `game::application_delegate_win32`, platform game-controller wrappers, `game::main_game_controller`, `gb::game_controller`, `gb::game_transition`, `gb::game_loop`, `gb::window_impl`.

**Important files.** `gbDemo/sources/main.cpp`, `gbDemo/sources/main.m`, `gbDemo/sources/application_delegate_*`, `gbDemo/sources/game_conroller_win32.cpp`, `gbDemo/sources/main_game_controller.cpp`, `gbCore/sources/game_controller.cpp`, `gbCore/sources/game_transition.cpp`, `gbCore/sources/game_loop*.cpp`, `gbCore/sources/window_impl_*.cpp`.

**Evidence.** `gbDemo/sources/main.cpp` allocates the Win32 delegate and enters `execute_runloop()`; `application_delegate_win32.cpp` owns the platform controller; `main_game_controller.cpp` schedules transition creation on a main-queue `thread_operation`; `game_controller.cpp` owns services/transitions and activates the selected transition; `game_transition.cpp` constructs passes/systems/scene and registers its feeder; `game_loop.cpp` invokes listeners and the main-thread job queue.

**Dependencies.** Platform UI frameworks/Win32, graphics and input contexts, configuration/resource accessors, transition XML.

**Public API.** `game_controller::add_transition()`, `goto_transition()`, `game_transition::add_system()`, `set_fabricator()`, `add_listener_to_game_loop()`.

**Typical flow.** Platform `main` creates an application delegate; it creates a platform controller and `window_impl`; `main_game_controller` queues creation of a `island_demo_transition`; `goto_transition()` calls `game_transition::on_activated()`; the transition builds render techniques and built-in systems, constructs its scene, then registers `ces_systems_feeder` with the game loop. Each native run-loop tick calls `game_loop::on_update()`.

**Add new functionality.** Put application transitions and scene selection in the application module (`gbDemo` or another executable); add reusable lifecycle capability to `gbCore` only when multiple applications need it.

**Normally do not modify.** Platform `main` files for gameplay features; `game_loop_*` for scene behavior; `gl_commands.hpp` merely to change one scene. Changing these has platform-wide impact.

## ECS architecture

### Entities and component storage

**Purpose.** Represent runtime objects as a scene-graph node with a fixed-capacity, type-indexed component set.

**Important classes.** `gb::ces_entity`, `gb::ces_base_component`; common specialized entities include `game_object_2d`, `game_object_3d`, `sprite`, `shape_3d`, `scene_graph`, and UI controls.

**Important files.** `gbCore/sources/ces_entity.{h,cpp}`, `ces_base_component.{h,cpp}`, `main_headers.h`, `game_object_2d.cpp`, `game_object_3d.cpp`.

**Evidence.** `ces_entity.h` declares the arrays, child containers, weak parent/feeder, construction template, and component API. `ces_entity.cpp` implements deferred construction, mask mutation, feeder notifications, attachment, and recursive feeder propagation. `main_headers.h` defines the lazy GUID macro. `ces_base_component.h` declares the weak owner backlink and protected setter.

**Dependencies.** `STTI_CLASS_GUID` in `main_headers.h`, `std::property_*` in `std_extensions.h`, `shared_ptr`/`weak_ptr`, `ces_systems_feeder` notifications.

**Representation.** An entity owns:

- `std::array<shared_ptr<ces_base_component>, 255> m_components`;
- a matching `std::bitset<255> m_mask`;
- unordered and ordered child collections, weak parent and weak feeder;
- tag and visibility state.

The runtime type ID is assigned lazily by `STTI_CLASS_GUID` from the insertion order into the component or system base class's GUID set. IDs start at 1, so slot zero is unused and only IDs 1 through 254 safely fit the 255-slot array; no bounds check protects a 255th registered type. IDs depend on first-use order within the process. No stable serialized entity ID is declared in `ces_entity`.

**Ownership.** Entities strongly own components and children. Children weakly reference parents. Systems retain matching entities as weak pointers. `ces_base_component` declares an owner weak pointer and `set_owner()`, but no definition or call to `set_owner()` was found in the inspected repository, including `ces_entity::add_component()`; component-to-owner access is therefore not an available evidenced facility.

**Reparenting caveat.** In `ces_entity::add_child()`, the attempted old-parent removal reads `ces_entity::parent` on `this`, rather than `child->parent`. The method then overwrites the child's weak parent and inserts it into the new parent's two strong child containers. Whether callers guarantee unattached children is `UNKNOWN`; do not assume `add_child()` safely reparents an already-attached child.

**Public API.** Always construct derived entities with `ces_entity::construct<T>(...)`, then use `add_component<T>()`, `get_component<T>()`, `remove_component<T::class_guid()>`, `add_child()`, and `remove_from_parent()`. `construct<T>()` is important because it sets `m_self_weak`, runs deferred component construction, then `setup_components()`.

**Typical flow.** A derived entity constructor queues default components with `add_deferred_component_constructor<T>()`; `construct<T>()` materializes them; later component changes notify the feeder; adding the entity under a scene root recursively assigns the feeder and queues membership evaluation.

**Add new functionality.** New reusable data belongs in a small `ces_*_component` derived from `ces_base_component`; new object presets belong in a derived entity whose constructor declares default components.

**Normally do not modify.** The 255-slot storage, `STTI_CLASS_GUID`, or entity construction sequence without a repository-wide migration. Never instantiate a derived entity with `std::make_shared` if it expects deferred/default components.

### Systems, registration, queries, and execution

**Purpose.** Maintain filtered entity lists and execute behavior in explicit order once per frame.

**Important classes.** `ces_base_system`, `ces_systems_feeder`, `ces_system_modifiers_component`.

**Important files.** `gbCore/sources/ces_base_system.{h,cpp}`, `ces_systems_feeder.{h,cpp}`, `game_transition.cpp`; representative systems: `ces_render_system.cpp`, `ces_box2d_system.cpp`, `gbDemo/sources/ces_car_boost_system.cpp`.

**Evidence.** `ces_base_system.cpp` stores mask-to-weak-entity vectors and implements enumeration/eligibility/cleanup. `ces_systems_feeder.cpp` queues membership changes, sorts registered systems, and contains the five execution loops. `game_transition.cpp` explicitly registers and orders the eight built-in systems. `gbDemo/sources/in_game_scene.cpp` explicitly registers application systems, mostly without assigning an order.

**Dependencies.** Component GUID masks, scene cameras, the global game loop, the scene root.

**Public API.** A system constructor builds one or more masks with `add_required_component_guid()` then registers them using `add_required_components_mask()`. Runtime logic uses `enumerate_entities_with_components()`. Registration is explicit through `game_transition::add_system()`. `set_order(ui8)` is optional in the API and defaults to 255; assigning intentional, unique order values is a safety recommendation, not a repository-enforced requirement.

**Typical flow.** Entity add/remove/component changes enter `ces_systems_feeder::m_changed_entities`. At the next update, every registered mask list is repaired. The feeder then calls all eligible systems in three global passes: every `on_feed_start`, every `on_feed(root, dt)`, every `on_feed_end`, followed by cleanup passes. Systems are sorted by `order`, but phase grouping means system A's `on_feed_end` never precedes system B's `on_feed`.

**Pause caveat.** `ces_base_system::can_be_feeded()` consults `ces_system_modifiers_component` on the root. The separate `set_is_paused()` field is written by demo scenes but is not read by `can_be_feeded()` or `ces_systems_feeder`; repository-wide search found no override of `can_be_feeded()`. Therefore those `set_is_paused()` calls have no evidenced effect on feeder execution. Whether this is intentional is `UNKNOWN`.

**Add new functionality.** Add engine-generic systems to `gbCore`; game-specific systems to the application. Register core defaults in `game_transition::on_activated()` only when every transition needs them; otherwise register in the scene's `create()`.

**Normally do not modify.** `ces_systems_feeder` for one system's logic; global system order numbers without checking all scene registrations. Avoid recursive traversal when a mask query expresses the requirement.

## Rendering architecture and RHI boundary

**Purpose.** Convert renderable ECS entities into ordered world-space passes, screen-space passes, an output pass, and presentation.

**Important classes.** `ces_render_system`, `render_pipeline`, `render_technique_base`, `render_technique_ws`, `render_technique_ss`, `render_technique_main`, `render_pass_descriptor`, `material`, `shader`, `texture`, `mesh_2d/3d`, `vbo`, `ibo`, `vao`, `graphics_context`.

**Important files.** `gbCore/sources/ces_render_system.cpp`, `render_pipeline.cpp`, `render_technique_*.cpp`, `render_pass_descriptor.cpp`, `material.cpp`, `shader.cpp`, `texture.cpp`, `vbo.cpp`, `ibo.cpp`, `gl_commands.{hpp,cpp}`.

**Evidence.** `ces_render_system.cpp` owns ECS filtering, pass traversal, culling, uniform upload, and draw dispatch. `render_pipeline.cpp` brackets frames and orders WS/SS/main techniques. `graphics_context.h` provides the shared context interface. `render_pass_descriptor.cpp` creates Vulkan/Metal descriptors but no OpenGL descriptor. `material.cpp`, `texture.cpp`, `vbo.cpp`, `ibo.cpp`, and `ces_render_system.cpp` contain backend preprocessor branches and native backend state.

**Dependencies.** ECS transform/geometry/material components and cameras; transition, technique, attachment, material, shader, and texture configurations; selected graphics API.

**Abstraction status.** The code has a shared rendering facade, not a complete interchangeable RHI. `graphics_context` abstracts context/frame presentation. `render_pass_descriptor` delegates to Vulkan or Metal implementations, while OpenGL techniques manage framebuffer state directly. `gl::constant`/`gl::command` supplies an OpenGL-shaped shared vocabulary. Resource classes expose common APIs but contain `#if USED_GRAPHICS_API` branches and backend handles; `material` owns Vulkan or Metal state directly. This conclusion is an **Inference** from the cited implementations—no class or module calls itself an RHI.

**Public API.** Normal game code supplies `ces_geometry_component` + transformation + `ces_material_component`; uses `scene_fabricator`; and selects technique names in material XML. Transition setup exposes `render_pipeline::add_ws_render_technique()`, `add_ss_render_technique()`, and `create_main_render_technique()` through importer inheritance.

**Typical flow.** `ces_render_system::on_feed_start()` begins the graphics frame. `on_feed_end()` binds each ordered WS technique, culls matching entities, binds each material, writes camera/model uniforms, binds/draws the mesh, and unbinds the pass. It then processes ECS render targets. `render_pipeline::on_draw_end()` draws ordered SS fullscreen passes, draws the main output fullscreen pass, ends Vulkan command recording when applicable, and presents.

**Add new functionality.** Add entity-level rendering through components/materials/fabricators. Add reusable pass behavior in `render_technique_*` plus configuration schema. A genuinely new backend feature usually touches the common resource class and each supported backend branch.

**Normally do not modify.** `ces_render_system` for a single material effect; generated configuration classes by hand; `gl_commands.hpp` selector casually; backend singleton teardown/order without validating a full frame.

### OpenGL backend

## Assets, shaders, and materials

### Asset loading and serialization

**Purpose.** Cache resources by filename/GUID and split CPU parsing from GPU/main-thread commit.

**Important classes.** `resource`, `resource_accessor`, `resource_loading_operation`, `resource_serializer`, `resource_commiter` and format-specific subclasses.

**Important files.** `resource*.{h,cpp,hpp}`, `texture_*`, `shader_*`, `mesh_3d_*`, `animation_3d_*`, `scene_2d_*`, `scene_3d_*`, `fcl_script_*`, `cubemap_texture_*`, `common_*.cpp`.

**Evidence.** `resource_accessor.hpp` creates/cache-registers typed resources and chooses synchronous versus queued work. `resource_accessor.cpp` starts the serializer thread and commits/callbacks in `on_update()`. Each `*_loading_operation.cpp` selects its serializer/committer by filename. `mesh_3d_loading_operation.cpp` accepts GB3DMESH/FBX; `animation_3d_sequence_loading_operation.cpp` accepts `.gb3danim`/`.GB3D_ANIMATION`; the scene/TMX/FCL loaders provide the other stated paths.

**Dependencies.** Bundle/document/custom search paths, libpng, ufbx, TMX parser, graphics API commit code, game loop.

**Public API.** `resource_accessor::get_resource<T_RESOURCE,T_LOADING_OPERATION>(filename, sync)` and `add_custom_resource()`. Resources expose loaded/committed state and callbacks/listeners.

**Typical flow.** Cache miss creates resource + operation. Async operations are serialized on the accessor's worker thread; the game-loop `on_update()` commits waiting operations and delivers callbacks. `sync=true` runs serialize+commit immediately, then queues callback delivery. Mesh FBX and GB3DMESH share the GB mesh committer after distinct serializers.

**Format caveat.** `texture_loading_operation.cpp` has a `.pvr` branch with no serializer assignment and only constructs a committer for `.png`; PNG is the only evidenced working texture-loading path. PVR support must be treated as unimplemented/unsafe, not as supported.

**Add new functionality.** A new format normally needs resource transfer data, serializer, committer, loading operation, resource type hookup, and a call site/fabricator. CPU decoding belongs in serializer; GPU object creation belongs in committer.

**Normally do not modify.** The accessor cache/worker for one asset type. Do not perform GPU commit on the worker thread. Do not hand-edit staged Windows assets when the source is in `gbBundle`.

### Shaders

**Purpose.** Load paired vertex/fragment sources and create backend shader/program state.

**Important classes/files.** `shader`, `shader_loading_operation`, `shader_serializer_glsl`, `shader_commiter_glsl`, `shader_compiler_glsl`, `built_in_shaders.h`; runtime GLSL sources in `gbBundle/Shaders/*.vert` and `*.frag`; Metal sources in `gbBundle/Shaders/metal/*.metal`.

**Evidence.** `shader_loading_operation.cpp` appends `.vert` and `.frag` to the supplied basename, then serializes and commits. `shader_compiler_glsl.cpp` performs OpenGL compilation and Vulkan shaderc compilation; its non-GL/non-Vulkan branch reports success without compiling. `mtl_device.cpp` loads the default Metal library, and `mtl_render_pipeline_state.cpp` resolves `vertex_<shader-guid>`/`fragment_<shader-guid>` functions. GLSL pairs and Metal sources are present under `gbBundle/Shaders`.

**Dependencies.** Material shader filename, GLSL compiler/OpenGL or shaderc/Vulkan, Metal default library conventions.

**Public API.** Materials call `resource_accessor->get_resource<shader, shader_loading_operation>(base_name, force)`; code sets standard and custom uniforms through `shader`/`material` methods.

**Typical flow.** Base name `shader_arrow` resolves to `.vert` + `.frag`; the serializer loads both. OpenGL compiles/links them, and Vulkan compiles them to shader modules. **Add new functionality.** Add both GLSL stages under `gbBundle/Shaders`, reference the base name from material XML, and add matching Metal functions under `gbBundle/Shaders/metal` for Apple targets. **Normally do not modify.** `built_in_shaders.h` for normal external shaders; shader loading operation just to add a shader pair. Do not assume GLSL is translated to Metal at runtime.

(order 7), and owns one shared wave clock. `ces_buoyancy_component` holds
probe/settings/state data; receiver uniforms carry per-prop wetness.
The source of truth for assets is `gbBundle`; the Windows build stages them.
See `ISLAND_DEMO.md` for controls, verification and platform limits.

The application-owned male resident uses `resident_navigation` and
`resident_behavior` CPU helpers plus `ces_island_resident_component/system`.
Its order-6 system chooses motion/clip in `on_feed_start` (before animation's
order-3 `on_feed`) and copies evaluated bones in `on_feed` (before render7).
`island_resident_demo` owns model setup and a weak-entity clothing listener;
the scene removes that listener on destruction. The resident has its own bone
and color buffers, independent of ocean receiver uniforms. Bulk legacy uniform
setters skip matrix arrays, so the demo forwards its bone array through the
existing individual material setter. PT4B's missing normals are handled by
derivative flat normals; its Metal descriptor is now supplied without changing
the 32-byte vertex layout. FBX preflight stays in the demo because synchronous
resource-loading failures can assert; canonical sources remain in `gbBundle`.
