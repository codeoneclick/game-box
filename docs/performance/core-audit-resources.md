# Core resource, scheduler, memory and lifecycle audit

Static audit of the current working tree, 2026-10-10. No code changed, executable run, build or dynamic measurement performed by this audit. Pre-existing changes were preserved. The engine map, flows, patterns, architecture issues and shared rendering/ECS instructions were consulted. The findings below establish implementation costs, not their measured share of frame time. Runtime confidence and impact remain conditional on workload; unused systems cannot be assessed from an island-scene capture.

## Measurement cautions

`game_loop.cpp:44` quantizes dt to whole milliseconds. Its FPS counter accumulates `clock()` only inside `on_update()` (`:41`, `:58-65`), excluding time before the next update. Platform semantics of `clock()` differ. Prefer external frame-to-frame monotonic timestamps, CPU thread samples and GPU timestamps when judging changes. Windows loop is unpaced except any renderer/presentation wait (`game_loop_win32.cpp:53-63`); pause skips listeners but still runs job update (`game_loop.cpp:46-56`). High paused CPU can therefore originate in the run loop rather than rendering.

Two additional details matter for these benchmarks: `vk_utils.cpp:143` copies the entire source buffer allocation rather than only the used bytes, so a short label can transfer its full 256-symbol capacity. Vulkan uniform source conversion also runs again for reflection in `shader.cpp:586-587` after compilation; parsing once into a reusable descriptor could avoid repeated regex/string work, although shaderc compilation is likely larger and must be measured.

None of these static findings justifies moving GPU commit to arbitrary workers. Fix synchronized ownership/ready queues first; then benchmark resource/transfer changes on Windows Vulkan and separately on Metal/OpenGL. The dormant backends and modules unused by the island scene remain dynamically UNKNOWN. The strongest future experiments are job/resource worker CPU accounting, upload/fence tail spikes, cold shader/FBX startup, and transition memory retention.
