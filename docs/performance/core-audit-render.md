## Current mechanisms and limits

Skinning already runs on GPU. `gbBundle/Shaders/shader_island_resident.vert:1` declares 64 bone matrices; `:5` performs four weighted bone transforms per vertex. Metal matches in `gbBundle/Shaders/metal/mtl_island_resident.h:7`. CPU pose evaluation and bone uploads remain, but moving vertex skinning onto GPU is not a new optimization.

Current Vulkan draw uniforms are already persistently mapped. `gbCore/sources/shader.cpp:1096` allocates a 2 MiB host-visible/coherent uniform buffer per shader per swapchain image and maps once at `:1103`. Do not characterize these uniforms as per-draw map/unmap, staging submits, or fence waits.

The 2 MiB arena and 1024 descriptor-set pool (`shader.cpp:1082`, `:1098`) have fixed capacity. Arena overflow is assertion guarded at `:1121`; descriptor exhaustion is checked at allocation. Resident bones use 4096 bytes per visible resident before other blocks/alignment. Record high-water usage before increasing population or pass participation. This is an explicit capacity concern, not evidence of current overflow.

Legacy `gbCore/sources/vk_uniform_value_buffer.cpp:35` maps/unmaps and synchronously stages uniforms, but no current shader call site was found. It is not an established current-frame hotspot.

Dynamic geometry differs: `gbCore/sources/vbo.cpp:542` and `ibo.cpp:133` map/copy/unmap on unlock and call `vk_utils::copy_buffers`. That helper allocates a command buffer, creates a fence, submits, waits, destroys/frees (`vk_utils.cpp:89`, `:121`, `:125`, `:128`, `:147`). When runtime measurements show dynamic uploads, batch them through a reusable staging arena. Distinguish creation/loading spikes from steady-frame activity. Keep GPU commit on its established game-loop thread.

Existing CPU batching is disabled (`gbCore/sources/ces_render_system.h:15`). It transforms and merges PTC vertices on CPU (`batch.cpp:125`, `:150`), with 16-bit capacities and caches keyed by mesh ID. It is not a ready-made replacement for independently animated residents. Hardware instancing is not used in the inspected mesh draw path; this is not a claim that no third-party/backend facility exists anywhere.

Other small CPU candidates: cache inverse-transpose normal matrices by transform version (`ces_render_system.cpp:487`); bind technique-list getter results by reference rather than copied `auto` (`:553`, `:142`); avoid copied Metal custom-buffer maps (`:523`, `:542`); retain render-target screen quad instead of creating it per render-target enumeration (`:586`). Prioritize only after measured CPU costs.

## Vulkan frame and attachment behavior

`gbCore/sources/graphics_context_win32.cpp:252` waits for the frame fence; `:263` waits for the acquired image's prior fence before `:267` begins its frame. `:301` submits one recorded frame command buffer. `:208` device-idle waits during teardown. No normal per-pass submission or queue-idle wait was found. Measure fence/acquire duration separately: waits may represent GPU work or pacing rather than CPU inefficiency.

Each offscreen pass always creates depth and stores it (`gbCore/sources/vk_render_pass_descriptor.cpp:155`, `:164`), including fullscreen field/AO passes. Color attachments always clear/store (`:131`). All equal-sized passes share pooled depth (`:302`). Dependencies at `:185` through `:195` order shader-read/color/depth use. Remove unused depth and optimize load/store only with Vulkan validation and captures; do not remove dependencies merely because they are visible in a timing trace.

Opaque base attachments use RGBA8 sRGB, RGBA8 SNORM, RGBA32F (`gbBundle/Configurations/techniques/ws_techniques/ws.technique.island_demo.xml:5`, `:7`, `:9`; native mapping `vk_render_pass_descriptor.cpp:388`). Seed/JFA/distance retain separate RGBA32F images. Reduced precision and field ping-pong can reduce storage and writes, but test precision over the -160..160 world domain and shoreline details. These are format/storage facts, not measured effective bandwidth.

Shared offscreen targets are not per-swapchain-image resources. Any future attempt to overlap frame graphs or parallel queues must inspect image ownership and dependencies as well as uniform fences. Static inspection does not establish a current cross-frame race, nor does it prove unrestricted overlap is safe.

## Metal and dormant OpenGL

Metal WS buffering is disabled at `gbCore/sources/mtl_device.cpp:15`, causing the WS command buffer to commit and waitUntilCompleted each frame at `:116`. SS/output use three-slot semaphores. Single-material MVP/custom buffers (`material.cpp:621`, `:1712`) are updated at offset zero (`mtl_buffer.cpp:66`). Enabling WS pipelining requires per-frame uniform storage first. SS/output reuse also merits an overwrite audit. Preserve or deliberately redesign the three command-buffer tracks and their ownership; source-only review does not quantify Apple GPU impact.

`material::get_custom_uniform_buffer` returns one buffer with an exact-size assertion for all vertex and fragment custom blocks (`material.cpp:1710`), while render submission updates it repeatedly (`ces_render_system.cpp:530`, `:547`). Multi-block materials need independent slices/storage. This is a correctness candidate independent of measured performance; Metal was not built or exercised.

Dormant OpenGL retains material state caches and scalar/vector/matrix equality checks (`material.cpp:1354`, `shader.cpp:672`). Arrays still upload through `set_custom_mat4_array` (`shader.cpp:747`). VBO/IBO updates use buffer-data wrappers (`vbo.cpp:537`, `ibo.cpp:128`). AO blur bypasses filtering on legacy GL2 (`gbBundle/Shaders/shader_ss_ssao_blur.frag:3`). Vulkan timings or compilation do not verify these guarded branches.

## Placement decisions

Keep fragment shading, distance propagation, AO, blur, SSR, and vertex skinning on GPU. Optimize their resolution, reuse, precision, and quality tiers before considering CPU migration. CPU should retain entity ownership, camera/frustum culling, render packet preparation, resource lifetime, and gameplay-required animation decisions. GPU instancing or palette storage is a later option for measured CPU draw/upload pressure, not a prerequisite for this audit. Compute animation or GPU-driven culling would add readback/lifetime/bounds complexity; no measurement here justifies that migration.

Future verification should record CPU render collection/descriptor/upload time, actual attachment dimensions/formats, per-pass GPU timestamps, API counts, frame waits, and allocation high-water marks using fixed scene/camera/population/settings. Compare cold-load and warmed steady-state frames separately. Build and exercise each changed backend; absent Metal/OpenGL runs remain UNKNOWN.
