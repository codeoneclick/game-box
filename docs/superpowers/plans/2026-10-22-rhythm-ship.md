# Rhythm Ship Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Launch a playable liner-deck rhythm demo in Game Box with preserved ocean/sky, 40 dancing pixel characters, metronome, scoring, energy and simulated competition.

**Architecture:** Dedicated application scene and transition reuse existing ocean and composition passes. Plain C++ track/session/leaderboard logic consumes a small audio transport; one ECS system animates the crowd. Scene helpers own environment, UI and input, keeping native audio and renderer details out of gameplay.

**Tech Stack:** Existing C++14 engine, ECS, JsonCpp, gbUI, configured GLSL/Metal materials, Windows PCM output, existing Apple audio_engine, PowerShell verification scripts.

**Spec:** `docs/superpowers/specs/2026-10-22-rhythm-ship-design.md` (approved by user on 2026-10-22).

## Global Constraints

- Preserve existing sky textures, water appearance, waves, horizon and atmospheric composition.
- Networking, CDN downloads, buoyancy, character movement, production music, skeletal dancing and a general sprite framework are outside this slice.
- Do not delete engine modules or rename legacy public APIs.
- Do not use frame count or accumulated visual delta as the clock.
- Construct derived entities through `construct<T>()`.
- GPU commits stay on the existing resource-accessor/game-loop path.
- Default BPM 128; 40 crowd characters; runtime crowd count 30-50; 10 bots with skills in [0.65,0.98].
- Hit windows: at most 40/80/130 ms; points 100/70/30/0; energy changes +0.025/+0.015/+0.005/-0.020; initial energy 0.35.
- Reuse current engine/dependencies. Do not hand-edit autogenerated, vendored or staged assets.
- Every source/resource addition must update applicable Visual Studio and Xcode membership in the same task.
- Build affected available targets and report Metal/OpenGL/Apple/server verification separately.

## Review Focus

1. Audio device initialization or playback failure: visible silent-clock fallback, monotonic time, no invalid handles or leaked buffers (Task 3).
2. A tap delivered after a frame stall: its recorded timestamp must be judged before the corresponding beat expires (Task 2).
3. Editing a debug field or clicking its controls: no gameplay taps or accidental restart; invalid windows preserve valid state (Task 7).
4. Restart or teardown during pending audio startup: old callbacks/input cannot mutate the new session or access destroyed entities (Tasks 3 and 8).
5. Material/pass bindings without island content: valid composition attachments, sky/ocean unchanged, no missing terrain/editor resources (Tasks 4 and 8).
