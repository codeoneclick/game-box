# Game Box Repository Instructions

## Purpose and source of truth

This repository contains the Game Box C++ engine plus its racing-game demo. The runtime combines an ECS with a hierarchical scene graph. Rendering has compile-time OpenGL, Vulkan, and Metal paths, but those paths are only partially abstracted.

Before changing engine behavior, consult:

- `ENGINE_MAP.md` for verified architecture, ownership, registration, and uncertainties.
- `ENGINE_FLOWS.md` for lifecycle and data-flow diagrams.
- `CODE_PATTERNS.md` for canonical implementation examples.
- `ARCHITECTURE_ISSUES.md` for known hazards.

Do not invent an API when these documents or source files do not establish one. State `UNKNOWN`, cite the files that need inspection, and continue with the narrowest safe work.

## Mandatory task routing

The `engine/` directory contains instructions, not engine source. Actual engine source remains under `gbCore/` and the other module directories. For every task, read the root instructions and each matching guide before editing:

| Task touches | Required guide |
|---|---|
| Entities, components, systems, ECS queries, system registration or feeder behavior | `engine/ecs/AGENTS.md` |
| Materials, shaders, meshes, textures, render techniques or render passes | `engine/render/AGENTS.md` |
| OpenGL-specific implementation | `engine/render/AGENTS.md`, then `engine/render/opengl/AGENTS.md` |
| Vulkan-specific implementation | `engine/render/AGENTS.md`, then `engine/render/vulkan/AGENTS.md` |
| Metal-specific implementation | `engine/render/AGENTS.md`, then `engine/render/metal/AGENTS.md` |

If a task crosses ECS and rendering, read both subsystem guides. Backend guides refine the shared render guide; they do not replace it.

## Module ownership

- `gbCore/`: reusable ECS, lifecycle, rendering, resources, scenes, input, Box2D integration, jobs, and configuration.
- `gbUI/`: reusable entity-based UI controls.
- `gbSound/`: audio engine and its ECS bridge.
- `gbDatabase/`: reusable SQLite wrappers. Application schemas stay with the application.
- `gbNetwork/`: ASIO transport, command handling, and network ECS integration.
- `gbDemo/`: racing-game application and the primary end-to-end usage examples.
- `gb_client_server_shared/`: shared gameplay/client-server sources compiled by consumers.
- `gbServer/`: server/sample executable; current build health is `UNKNOWN` because project references are stale.
- `gbBundle/`: canonical runtime assets and configuration.
- `gbWin32SharedResources/`: flattened generated/staged Windows assets. Do not edit these as source assets.
- `gbCore/autogenerated/`, `gbDemo/autogenerated/`: generated configuration code. Do not hand-edit.
- `gbCore/libraries/`, `gbDemo/Pods/`: vendored dependencies. Do not edit unless the task explicitly targets the dependency.

Put reusable behavior in its owning engine module and application-specific behavior in `gbDemo` or the relevant executable. Do not move game rules into `gbCore` merely because an engine type is convenient.

## Standard workflow

1. Run `git status --short` and preserve unrelated or pre-existing changes.
2. Route the task using the table above.
3. Locate the canonical example named by the subsystem guide and inspect both its declaration and implementation.
4. Trace ownership, registration, lifecycle timing, and backend branches before editing.
5. Make the smallest change consistent with existing naming and file layout.
6. If adding a source file, add it to every applicable `.vcxproj` and Xcode target. File presence alone does not compile it.
7. Run the narrowest relevant checks plus the documented build/smoke test. Report every target or backend not verified.

For short prompts, infer routine details from existing patterns. For example, “Add a HealthComponent” means find the nearest component pattern, put reusable ECS data in the owning module, use the required STTI declaration, update build metadata, and verify it. Ask only when a choice would materially change public behavior or module ownership.

## Global architectural rules

- Construct derived entities with `gb::ces_entity::construct<T>(...)` when they rely on deferred/default component setup.
- Treat component/system GUID allocation, the 255-slot component array, entity attach/detach, and feeder phase order as high-risk contracts.
- Runtime scene roots are `scene_graph` subclasses owned by `game_transition`; serialized `scene_2d`/`scene_3d` resources are not runtime scene roots.
- CPU asset serialization may run on a resource worker. GPU commit and resource callbacks run from `resource_accessor::on_update()` on the game-loop path. Do not move GPU work to the serializer worker.
- Rendering is a shared facade with backend branches, not a pure plug-in RHI. A shared resource/material/pass change may require OpenGL, Vulkan, and Metal work.
- Preserve legacy public spellings such as `game_conroller`, `commiter`, and `transfering` unless the task explicitly requests a migration.

## Files normally not modified for local features

- `gbCore/sources/main_headers.h`
- `gbCore/sources/ces_entity.*`
- `gbCore/sources/ces_systems_feeder.*`
- `gbCore/sources/gl_commands.*`
- platform presentation/synchronization code in `graphics_context_*`, `vk_*`, and `mtl_device*`
- `resource_accessor.*`
- generated or vendored sources

If the requested behavior truly requires one of these, isolate the change, explain the invariant being altered, inspect all consumers, and expand verification accordingly.

## Build and verification

No engine-owned automated test suite was discovered. Use compile checks and focused demo smoke tests; do not describe them as unit tests.

The evidenced Windows demo build is:

```powershell
./gbScripts/build-gbDemo.ps1 -Configuration debug-client -Platform x64
```

It requires Visual Studio/MSBuild and a machine-level Vulkan SDK. It builds `gbCore`, `gbSound`, `gbDatabase`, `gbUI`, `gbNetwork`, and `gbDemo`, then stages assets and shaderc.

Before completion:

1. Run `git diff --check` for tracked changes and inspect `git status --short` for new files.
2. Build every directly affected available target.
3. Run the affected demo flow when behavior, assets, ECS execution, or rendering changed.
4. For backend-specific changes, build and exercise that backend. A Windows Vulkan build does not verify OpenGL or Metal.
5. Report commands run, outcomes, and anything left `UNKNOWN`.

Do not use `gbCore/gbCore.sln` as proof of a green build: it references the absent `gbAnimation` project. Do not claim `gbServer` builds without separately resolving or accounting for its absent shared sources.
